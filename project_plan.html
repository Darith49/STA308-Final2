University Data Portal (Django): Detailed Project Plan

STA308 Final Project | Upload XLSX → automatic cleaning → live charts (Chart.js, optional Superset)

Assumptions (edit if wrong): 12-week timeline, solo or team of 2-3, Python 3.11 + Django 5.x, PostgreSQL (SQLite for early dev), Chart.js as the primary charting layer, Superset as an optional stretch. The "university data" is student/course/grade-style spreadsheets. Because this is a statistics course, the plan emphasizes defensible statistical cleaning and a data-quality report, not just a working website.

1. Project Definition

1.1 Problem Statement

University staff and students keep data in messy Excel files: inconsistent headers, mixed date formats, duplicate rows, missing values, typos in categories. Cleaning is manual, undocumented, and not reproducible, and turning the result into charts is a second manual step.

1.2 Goal

Build a Django web portal where an authenticated user uploads an XLSX file, the backend validates and cleans it automatically using documented rules, produces a data-quality report of everything it changed, and renders interactive, live-updating charts from the cleaned data.

1.3 Objectives (SMART)

# Objective Measure of success
O1 Secure upload of .xlsx files Rejects invalid/oversized/malicious files in 100% of test cases
O2 Automatic cleaning pipeline with 10+ rule types Every change logged; cleaning reproducible from the log
O3 Data-quality report per upload Before/after stats: rows, missing %, duplicates, outliers
O4 Interactive charts (4+ chart types) Chart.js dashboard renders from a JSON API in under 3 s for 50k rows
O5 "Live" behavior Dashboard updates without page reload when processing finishes or new data arrives
O6 User accounts and data isolation Users only see their own uploads (verified by tests)
O7 Tested, deployed, documented 70%+ coverage on cleaning code; public URL or Docker setup; full report

1.4 Research / Evaluation Questions (important for a stats course)

  • RQ1: How accurate is the automated cleaning compared with manual cleaning? (Compare against a hand-cleaned "gold" file.)
  • RQ2: How does each cleaning rule affect summary statistics (mean, SD, correlation) of the dataset?
  • RQ3: How much time does the portal save versus manual cleaning in Excel? (Small user study, 5+ people.)
  • RQ4: How well does it scale (rows vs processing time)?

1.5 Scope

In scope: upload, validation, cleaning, quality report, dashboards, user accounts, export of cleaned data (CSV/XLSX), tests, deployment. Out of scope: real university database integration, single sign-on, machine-learning predictions, CSV/Google Sheets import (listed as extensions).

Level Behavior Effort

L2 Page shows processing progress and auto-renders charts when cleaning finishes (polling or Server-Sent Events) Must

Honest note on Superset: Superset is a separate, heavy application (own database, Docker stack, own users). It is not a library you import into Django. Integrating it means: running it alongside Django, pointing it at the same PostgreSQL where cleaned data is stored, and embedding dashboards in your pages (embedded dashboards + guest tokens). Exact configuration steps change between versions, so verify against the current Superset docs before committing. Recommendation: build everything with Chart.js first (core deliverable), and treat Superset as an optional Week 10-11 add-on only if you're ahead.

4. The Cleaning Pipeline (core of the project)

4.1 Pipeline Stages

  1. Ingest: read every sheet with openpyxl/pandas (read_only=True for big files); skip empty sheets; record merged cells and hidden rows/columns.
  2. Structure detection: find the real header row (first row with mostly non-empty, mostly string cells), drop title/notes rows above it, drop trailing total/blank rows.
  3. Header normalization: trim, lowercase, replace spaces/symbols with underscores, deduplicate (score, score_2), fill blank headers (column_3).
  4. Type inference: per column, try numeric → date → boolean → category → text using a majority-vote threshold (e.g., 90% of non-null values parse).
  5. Value standardization: trim whitespace, normalize case for categories, unify null tokens (N/A, NA, -, null, empty string), fix numeric strings ("1,234", "85%", "A+" handling by column type).
  6. Date handling: parse mixed formats; flag ambiguous day/month (03/04/2024) and report the assumption; convert Excel serial numbers.
  7. Duplicates: exact-row duplicates removed (keep first); optional key-based duplicates (e.g., same student_id + course) flagged, not auto-deleted.
  8. Missing values: report per column; apply strategy by type (see 4.3).
  9. Outliers and invalid values: range checks (grade 0-100, age 15-100), IQR / modified z-score flagging (flag by default, never silently delete).
  10. Categorical typo repair: fuzzy matching within a column (e.g., rapidfuzz ratio ≥ 90 maps "Computr Science" → "Computer Science"); always logged and reversible.
  11. Integrity checks: ID uniqueness, referential checks if multiple sheets share keys, cross-column logic (end date after start date).
  12. Profile and report: compute before/after statistics and a quality score.
  13. Persist: save cleaned data, actions, report, and mark status DONE.

4.2 Rule Catalog (document each in docs/rule_catalog.md)

Rule ID Name Action Default
R01 Header row detection Re-index header On
R02 Header normalization Rename columns On
R03 Drop empty rows/cols Remove On
R04 Whitespace trim Modify On
R05 Null token unification Modify On
R06 Numeric coercion Modify; failures → NaN + log On
R07 Date parsing Modify + ambiguity flag On
R08 Exact duplicate removal Remove On
R09 Category case/typo fix Modify On (threshold adjustable)
R10 Range validation Flag On
R11 Outlier flagging Flag only On
R12 Missing-value handling Impute or flag Flag only; imputation opt-in
R13 Key duplicate detection Flag On
R14 Cross-column consistency Flag On

Principle: destructive actions (removing rows) are limited to blank rows and exact duplicates; everything else modifies with a log entry or flags. The original file is never altered, and the user can download both versions.

4.3 Missing Value Strategy (tie to statistics)

Situation Default Justification to put in report
Column > 50% missing Flag, suggest dropping Too little information
Numeric, < 5% missing Leave blank (default) or median impute (opt-in) Median is robust to outliers
Categorical missing Fill with "Unknown" (opt-in) Preserves rows
ID/key missing Flag row as invalid Cannot join/identify
Discuss MCAR/MAR/MNAR briefly and why blanket mean imputation can bias variance estimates.

4.4 Data Quality Report Contents

  • Summary: rows/columns before and after, rows removed, cells modified, flags raised
  • Per-column table: inferred type, missing % (before → after), unique count, min/max/mean/SD/skew, outlier count
  • Action log (filterable): rule, column, before → after, reason
  • Distribution comparison (histograms before vs after for key numeric columns)
  • Quality score (0-100): e.g., weighted average of completeness, validity, uniqueness, consistency. Define the formula explicitly and justify the weights.
  • Downloadable as HTML/PDF/XLSX (extra sheet "Cleaning Log")

4.5 Configurable Options (per upload)

Fuzzy-match threshold, imputation on/off and method, outlier method (IQR vs z-score), valid ranges per column, which columns are keys. Provide sensible defaults and a "Re-run with options" button.

4.6 Performance

Use vectorized pandas, avoid row loops, read with usecols/dtype where possible, cap at e.g. 100k rows / 20 MB for the course project, and benchmark 1k, 10k, 50k, 100k rows (feeds RQ4).

5.2 API Design (DRF)

Endpoint Method Purpose
/api/uploads/ POST Upload file
/api/uploads/ GET List own uploads
/api/uploads/<id>/status/ GET status, progress_pct
/api/uploads/<id>/report/ GET Quality report JSON
/api/uploads/<id>/columns/ GET Column profiles
/api/uploads/<id>/chart-data/?type=bar&x=dept&y=gpa&agg=mean&filters=... GET Aggregated data for a chart
/api/uploads/<id>/download/?version=clean GET Cleaned file
/api/dashboards/ CRUD Saved dashboard configs

Rules: aggregate on the server (never send 100k raw rows to the browser), validate column names against the dataset's schema (prevents injection), paginate tables, cache repeated aggregations.

5.3 Live Update Mechanisms

  • L2 (must): after upload, the page polls /status/ every 1-2 s, shows a progress bar and stage name ("Cleaning dates…"), and calls renderDashboard() when status = DONE. Alternative: Server-Sent Events.
  • L3 (should): Django Channels + Redis pushes a message to a per-dataset group when a new version finishes; the dashboard re-fetches. If Channels is too heavy, use 10-second polling for the dashboard and say so honestly.
  • Filters (dropdowns, date range, sliders) trigger new API calls and chart update() with animations; debounce input.

5.4 Dashboard UX

Grid of chart cards (add/remove/resize), global filter bar, KPI tiles (rows, columns, quality score, missing %), "Save dashboard," "Export chart as PNG," and "Download data." Use colorblind-safe palettes, readable axis labels, titles with units, and tooltips.

5.5 Superset Integration (optional, Weeks 10-11)

  1. Run Superset via Docker Compose next to Django and PostgreSQL.
  2. Store cleaned data in per-upload tables in a dedicated schema (clean_data); register that database in Superset.
  3. Create datasets/charts/dashboards in Superset; enable embedding and request guest tokens from your Django backend to embed in an <iframe>/Embedded SDK.
  4. Handle row-level security so users only see their data. Risks: heavy RAM use, configuration friction, version differences. Mitigation: timebox to 4-5 days; if it's not working by then, drop it and document the attempt in the report as "future work."

6. Security and Privacy (high-value section for grading)

Threat Mitigation
Malicious file disguised as .xlsx Check extension and magic bytes/zip structure; open only with openpyxl/pandas; never execute content
Zip bomb / huge file Max upload size (e.g., 20 MB), cap uncompressed size and rows/columns, timeout on processing
XLSM macros / external links Accept .xlsx only; ignore formulas' external references; read values only (data_only=True)
Formula injection on export (=CMD(...)) Prefix cells starting with = + - @ with ' when writing exports
Path traversal / filename tricks Store with random UUID names, never use user filename in paths
IDOR (accessing others' uploads) Queryset filtered by owner=request.user on every view/API; tests for it
CSRF/XSS Django defaults on; escape all user-derived text (column names, cell values) in templates and chart labels
SQL injection ORM only; whitelist column names; if per-upload tables are used, sanitize identifiers
Sensitive student data Warn users not to upload real personal data; auth required; HTTPS; data retention policy (auto-delete after N days); no logs of cell values
Brute force Rate limiting on login/upload (django-axes or throttling in DRF)
Secrets Environment variables, .env not committed, DEBUG=False in prod

Generate messy files by injecting known errors into a clean synthetic file with a script (you then know the exact ground truth and can compute precision/recall of the cleaning).

7.2 Test Types

Level Examples
Unit Each rule: input DataFrame → expected output + log entries
Property-based (hypothesis) Cleaning is idempotent (clean(clean(x)) == clean(x)); row count never increases
Integration Upload → status DONE → report present → chart-data endpoint returns correct aggregates
Security Upload non-xlsx, oversized file, other user's upload ID returns 404/403
API Status codes, schema, filters, invalid columns
UI/manual Chrome/Firefox, mobile width, accessibility check (Lighthouse)
Performance Time vs rows (1k → 100k), memory

Target: 70%+ coverage overall, 90%+ on cleaning/. Use GitHub Actions to run tests on every push.

7.3 Evaluation of Cleaning Accuracy (RQ1)

With injected errors: compute for each rule precision (fixes that were correct / fixes made) and recall (injected errors found / injected errors). Report in a table. Compare cell-level agreement between pipeline output and gold_clean.xlsx.

7.4 Usability Study (RQ3)

5-8 participants. Task: clean a provided messy file and make 3 charts in (a) Excel and (b) your portal. Record time, errors, and a SUS (System Usability Scale) questionnaire. Report mean times, SUS score, and a paired comparison (paired t-test or Wilcoxon with justification, noting the small sample).
